# Hardware wallet retry after an unknown broadcast

These checks cover an ordinary hardware-wallet on-chain send whose broadcast outcome is unknown. Rebroadcasting the same signed transaction cannot pay twice because the txid stays the same, while a new signature can create a second payment. Broadcast faults are not in the journey Capabilities table, so this is a manual recipe. The same file applies to iOS and Android.

## Setup

- Use a disposable regtest wallet paired with the Bridge emulator and funded for several sends. Follow [the suite setup](README.md#prerequisites). Never use an existing wallet or real funds.
- Run a local Electrum JSON-RPC proxy between the app and the regtest Electrum server, and point the app's Electrum server setting at it. No such proxy is in this repo, so supply your own. It forwards every method unchanged, except that for `blockchain.transaction.broadcast` it can switch between pass-through and these faults: forward then return an error, swallow then return an error, hang without replying, return a given refusal, and refuse connections. A true connection refusal requires stopping the proxy (see check 6).
- Have the proxy log each broadcast's raw transaction, so that two attempts can be compared and the txid read with `decoderawtransaction`.
- Use `getrawmempool` on the regtest node as the record of what reached the network. Use the emulator's own screen and controller to see whether a device prompt appeared. Do not rely on local activity as proof of either.
- Mine with the suite's usual command between checks, so that each check starts with an empty mempool. Mining does not clear an observed record, so use a new address or amount for each check. Forward-then-error makes the transaction visible, so a wallet sync can mark the record as observed before you act. That must not change what Retry does.

Fee rate and tags do not decide whether two payments match; only the wallet, address and amount do.

## Checks

Unless a step says otherwise, the first attempt is a normal send approved on the emulator, and the sign screen's button reads Retry after a failure. Set pass-through before a retry that should succeed.

1. **Retry uses the same transaction.** Send with forward-then-error, then set pass-through and tap Retry. Expected: a "Transaction may have been sent" toast after the first attempt, no device prompt on retry, the same raw transaction and txid in both proxy log entries, Success, and one transaction in `getrawmempool`. The watcher seeing the transaction first must change nothing about Retry: repeat the check and tap Retry only after the transaction shows in activity, and expect the same result.
2. **Leaving and reopening keeps Retry.** Send with swallow-then-error, leave the send sheet, and start again to the same address and amount. Change the fee preset first if one is offered. Expected: the review shows the original fee and the fee cannot be edited, the sign button reads Retry, and after pass-through the retry succeeds with no device prompt and the original txid.
3. **A different amount warns first.** Send with swallow-then-error, leave, and start again to the same address with a different fundable amount. Repeat once with a different address. Expected: swiping to send on the review shows the "Transaction may have been sent" alert with Cancel and Yes, Send before any device prompt. Cancel stays on the review, with no device prompt and the record kept. Yes, Send deletes nothing and continues to the sign screen, which signs anew on the emulator with a new txid. The original record is replaced only once the new transaction has been signed, just before it is broadcast. Separately, tap Yes, Send, reject on the emulator or tap Back on the sign screen without signing, and start the original payment again. Expected: it still retries the original bytes with no device prompt, and the different payment warns again before any device prompt, because leaving the sign screen loses Yes, Send. Separately, repeat the send after Yes, Send, reject on the emulator, and tap again on the same screen, for both a different payment and a repeat of an observed one (check 4). Expected: the button keeps its sign label rather than Retry, the tap asks the device for a new signature, no Success appears for the old transaction, and the proxy log shows only the new bytes. Yes, Send lasts until a new transaction has been signed.
4. **Force quit keeps the record, and observing the transaction does not delete it.** Send with swallow-then-error, force quit, relaunch, and start again to the same address and amount. Expected: Retry with the original fee, and no device prompt. Then send a fresh payment with forward-then-error, force quit, relaunch, and wait for the wallet to sync. Expected: once the transaction shows in the hardware wallet's activity, the record is marked as observed and stays marked after a restart. A new send to the same address and amount shows the alert from check 3 before any device prompt, and only Yes, Send signs anew. Tap Yes, Send, then Back on the sign screen without signing, and swipe again. Expected: the alert shows again, with no device prompt until Yes, Send, because the original stays protected until a replacement is signed. A new send to a different address or amount shows no alert and signs normally. If that send fails before it is signed, for example with the device disconnected, a new send to the original address and amount still shows the alert.
5. **A hang does not lock navigation after the timeout.** Send with the hang fault and wait more than 120 s. Expected: back navigation and sheet dismissal are ignored while the sign screen is still waiting, then the "Transaction may have been sent" toast at the timeout, and both work after it. Go back, set pass-through, and retry the same payment. Expected: no device prompt, the original txid and one mempool transaction. Current Android behaviour: the 120 s timeout does not fire against a silent open socket, because the native call cannot be cancelled, so the sheet stays blocked until the socket closes. This is pre-existing and not fixed here. On Android, close the proxy's socket to end the wait before the retry.
6. **Refused connections do not block.** Stop the proxy so that connections are truly refused, and send. Expected: the connectivity toast, and the app stays usable with back navigation working. Retry in the same sheet after restarting the proxy with pass-through broadcasts the same bytes with no device prompt. Separately, leave the sheet after the failure: a new send to the same payment asks for the device again, because nothing reached the network. A connection reset after accept is an unknown outcome, so it keeps the record and shows "Transaction may have been sent". That is intended.
7. **A first-attempt refusal releases.** Return the refusal `min relay fee not met` on the first attempt. Expected: a failure toast, and the next attempt prompts on the emulator and produces a new signature, with no retained-send warning.
8. **A retry refusal warns and does not re-sign.** Send with swallow-then-error, then tap Retry with the refusal `bad-txns-inputs-missingorspent`. Expected: the "Transaction may have been sent" toast and no device prompt. Leaving and returning to the same payment shows the alert from check 3 before any device prompt, because a refusal on a retry may describe our own earlier accepted transaction. Only Yes, Send signs anew. If the watcher has already seen the transaction, the same refusal on a retry ends in Success with the original txid and no device prompt.
9. **A hardware transfer warns before it signs over a kept send.** Android only: iOS has no hardware transfer sign screen, because its Transfer To Spending button opens the Transfer Unavailable sheet. This needs the Spark setup from [transfer-to-spending.xml](transfer-to-spending.xml). Send with swallow-then-error, leave the send sheet, and set pass-through. Start Transfer To Spending from the same hardware wallet, continue to the sign screen (testTag `HardwareTransferSign`), and tap "Open Trezor Connect". Expected: the alert (testTag `SendDialogRetainedHardwareSend`) shows with Cancel and Yes, Send before any device prompt. Tap Cancel. Expected: the sign screen stays open, with no device prompt and nothing new in the proxy log. Tap "Open Trezor Connect" again. Expected: the alert shows again. Tap Yes, Send, then reject on the emulator. Expected: the device prompt appears only after Yes, Send. Leave the transfer and start the original send again to the same address and amount. Expected: the review shows the original fee and the button reads Retry, because the kept record is intact. Back out without tapping Retry, start the transfer again, tap Yes, Send, and approve on the emulator. Expected: the transfer is signed and broadcast with a new txid, the kept record is replaced only then, and a later send to the original address and amount prompts the device with no Retry.

## What the Bridge emulator cannot prove

The emulator reaches the app through Trezor Bridge on the host. These runs say nothing about USB, BLE, THP pairing, Jade, or real hardware. Report those as untested. Unit tests cover the retained-send outcomes for each error, but injected state is not proof of a native broadcast fault.

Record the platform, exact build, proxy faults used, observed results and untested cases separately. One platform's results do not establish the other's.
